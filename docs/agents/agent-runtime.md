# Agent runtime: tool inventory, turn flow, sessions

Agent-facing detail for the backend request path, linked from `AGENTS.md`; the user-facing overview is `docs/architecture.md`.

## Tool inventory

The backend embeds the **Pi SDK** (`@earendil-works/pi-coding-agent`) and runs a **single flat agent** with built-in tools (`read`/`bash`/`edit`/`write`/`grep`/`find`/`ls`), a `subagent`/`bg_wait` delegation pair (the [pi-subagents](https://github.com/nicobailon/pi-subagents) extension package), an `interview` clarifying-questions tool (a native re-implementation of [pi-interview](https://pi.dev/packages/pi-interview) — see `server/src/agent/interview.ts`; the form renders inline in the chat UI instead of the package's own browser window), the [pi-web-access](https://pi.dev/packages/pi-web-access) web tools (`web_search`/`fetch_content`/`get_search_content`/`source_check`), live PDF annotation tools (`add_pdf_annotation`/`list_pdf_annotations`/`remove_pdf_annotation`), a hybrid durable Modal tool family (`modal_run`/`modal_submit`/`modal_status`/`modal_wait`/`modal_cancel`/`modal_results`/`modal_submit_batch`; `server/src/agent/modal-tool.ts`), a `generate_image` tool (Pi 1.0 image models, saved into the sandbox; `server/src/agent/image-tool.ts`), and MCP tools through **Pi's built-in MCP support** (project `.pi/mcp.json` + global `<agentDir>/mcp.json`; see the MCP caveat below). PDF annotations and Modal jobs are also available to child agents through the vendored `kady-pdf-annotations` and `kady-modal` Pi packages; annotation sidecars use a shared cross-process lock and atomic replacement. Modal jobs are server-owned and restart-recoverable. There is no orchestrator/expert split and no model proxy: models go directly to **OpenRouter**, connected Pi OAuth providers (`openai`, `openai-codex`, `anthropic`, `github-copilot`, `xai`, `kimi-coding`, `meta`), **NVIDIA NIM** (API key), or a local **Ollama** / OpenAI-compatible server. Everything runs locally; user data lives in `projects/`.

## How a turn flows

- **UI → backend.** A chat tab posts to the TS backend. Each tab carries its own `sessionId` (a Pi JSONL session); requests are scoped to a project via the `X-Project-Id` header (→ `?project` → `kady-project` cookie → `default`), resolved in an `onRequest` hook using `AsyncLocalStorage` (`server/src/scope.ts`).

- **Sessions.** `server/src/agent/session-registry.ts` holds live Pi `AgentSession` objects (one per tab, ≤10 per project) and persists each as a JSONL file under `projects/<id>/sandbox/.pi/sessions/`. `ModelRuntime` + `ModelRegistry` are process singletons; the runtime uses Kady's shared Pi auth store.

- **Streaming.** `POST /sessions/:id/run` calls `session.prompt()` and streams an SSE schema mapped from Pi's `AgentSessionEvent` (`server/src/agent/events.ts`): `text_delta`, `thinking_delta`, `tool_start/update/end`, `turn_start/end`, `error`, a terminal `cost` frame, and `done`. The run body may carry inline **image attachments** (`images: [{data, mimeType}]`, base64; validated by `server/src/agent/prompt-images.ts` — ≤12 × 5MB, png/jpeg/webp/gif) that ride the user message as Pi image blocks so the model sees them directly; the composer collects them via paste/drop/file-picker (`web/src/lib/image-attachments.ts` downscales >3MB client-side), other file types keep the sandbox-upload path, steering stays text-only (image sends mid-run queue instead), and `GET /sessions/:id/history` replays them for reopened tabs. The run route is a thin wrapper around `server/src/agent/run-pipeline.ts` (`claimRun` → `openRun` → `executeRun`: claim before the first await, `run_start` before model setup, ledger before the in-flight budget entry is dropped). A permanent per-session observer (`server/src/agent/session-observer.ts`, hooked in via `setSessionObserver`) reuses that pipeline to adopt turns Pi extensions start on an idle session as **system runs**: scheduled-run notices arrive as `pi.sendMessage` custom messages with `triggerTurn: true`, while since pi-subagents 0.77 completions and supervisor requests reaching an idle lead are appended without a turn and the lead is woken by a fixed user prompt (`PARENT_WAKE_TEXT`, `sendUserMessage(…, { deliverAs: "steer" })`). That prompt is plumbing addressed to the model, so `subagent-wake.ts` (parity-tested against the installed package) blanks its `message_start` frame — the client still takes it as the run's prompt echo — and history, notebook/repro exports and chat snapshots skip it. System runs are `RunMetadata.origin: "system"`, ended on `agent_settled`, aborted when over the cap; a custom message with no turn becomes a `kind: "notice"` run. Custom messages (`role: "custom"`) reach the client as `message_start` frames carrying `customType`, text and a per-type whitelist of scalar `details` (`CUSTOM_MESSAGE_DETAIL_KEYS` in `events.ts`), appear in history as `role: "system"`, and render as `SystemCard`s; idle tabs poll `run/state?frames=0` to attach to runs they did not start.

## Session lifecycle and extensions

- **`session.bindExtensions()` is what fires `session_start`.** Pi's SDK emits `session_start` (and runs `resources_discover`) only from `AgentSession.bindExtensions()`, never from `createAgentSession()`. `session-registry.ts` calls it with `mode: "print"` after every build and emits `session_shutdown` through `session.extensionRunner` on release. Skipping it looks harmless — `subagent`/`bg_wait` are registered at extension load — but pi-subagents starts its supervisor channel (and registers the lead's `subagent_supervisor` tool) only in its `session_start` handler, so the allowlist entry is dead without the call. Cold-opened sessions start on the model they last ran with (`restoredSessionModel`, resolved through Kady so synthesized local/catalogue models survive reopening; authentication is still required and a bare Fusion wire id is not restored), brand-new ones on the project's latest chat model (`latestProjectModel`; the resident scheduler session always uses that policy), because extension-initiated system runs use the session's current model and the global default is the most expensive one.

## Interview tool

- **Interview tool (clarifying questions).** The `interview` custom tool (`server/src/agent/interview.ts`) blocks the run on a pending-answer promise; the questions ride the normal `tool_start` SSE frame and the chat UI renders them as an inline form (`web/src/components/interview-form.tsx`), POSTing answers to `/sessions/:id/interview/:toolCallId`. Tool `promptGuidelines` + the seeded `AGENTS.md` ask for blocking ambiguity or missing authorization while allowing routine reversible choices within scope. Question schema mirrors pi-interview (single/multi/text/image/info, recommended/conviction/weight, code `content`, image/table/mermaid/chart/html `media`); user-uploaded images return to the model as image blocks. Deliberately NOT exposed to sub-agent child processes — they route blocking questions through `contact_supervisor`; the lead resolves them from existing instructions or interviews the user before replying.

## Compaction

- **Compaction is science-aware.** `server/src/agent/compaction-bridge.ts` hooks Pi's `session_before_compact` and returns a full `CompactionResult`: a deterministic preamble built from Kady's stores (`buildCompactionPreamble`: notebook entries, latest frozen plan, `scientific_result` step ids, latest `environmentId`, authored execution states/corrections and pending Modal jobs) plus a bounded public specialist-status snapshot, followed by a narrative generated with Pi's exported `generateSummaryWithUsage` under `SCIENCE_COMPACTION_INSTRUCTIONS` (Pi appends them as "Additional focus" to its coding checkpoint format, so they map those sections onto research work and add a `## Scientific Record` section; the history call also sees the records block, the split-turn prefix call gets `TURN_PREFIX_FOCUS` instead); split turns get a second call like Pi's own. Only the narrative of an earlier Kady summary is reused (`previousNarrative`): its records would hand the model stale job/specialist states to preserve and nest one preamble in the next. Pi ignores the `details` of hook-made compactions (`fromHook`), so the `<read-files>`/`<modified-files>` lists are carried by parsing the previous summary (`compactionFileLists`). Pi's serializer keeps only the first 2,000 chars of a tool result, so longer ones are clipped to head + tail first (`clipToolResultsForSummary`). Returned `usage` lands on the compaction entry and in `getSessionStats()`, so it is ledgered. Any failure returns `undefined` (Pi's default runs); the hook never cancels. `POST /sessions/:id/compact` is the manual path (409 while streaming/claimed, 402 over cap, ledgered from the stats delta); `GET/PUT /projects/:id/compaction` edits `compaction.*` in `sandbox/.pi/settings.json` via `compaction-settings.ts` (malformed file → 409, never rewritten). `compaction_end` reaches the client as a `customType: "compaction"` frame.
