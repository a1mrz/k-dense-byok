# Delegation: subagents, specialists, schedules

- **One flat agent.** Delegation uses pi-subagents native Pi sessions, usually in a detached runner. `subagent-runtime-settings.ts` seeds `forceTopLevelAsync: true` in `<agentDir>/extensions/subagent/config.json` (write-if-missing) and removes the old ineffective project key. `subagent-control.ts` registers public preflight, capability ceilings, required child extensions and session-scoped Modal background work. Required packages provide guard, notebook, Modal, PDF, web and MCP support even with ambient discovery disabled; `kady-child-runtime` also registers tools in foreground children where `PI_SUBAGENT_CHILD` is absent. `scripts/patch-subagents.mjs` applies exact-version, anchor-checked host seams at install/startup: child streams, watchdog reviews/permission arbiters, stable fleet control targets, and `KADY_HOST_NO_DRAIN_V1` — Kady sessions are headless to Pi (`bindExtensions({mode:"print"})`, no UI context), so pi-subagents' `agent_end` handler would `drainOutstandingWork` (wait up to 30 min for every async run and background-work provider) and, since Pi awaits extension `agent_end` handlers before a run settles, hold the user's chat turn open; the seam skips it for ids in `globalThis.__kadyInteractiveSessions` (filled by `subagent-control.ts`), and completions still arrive as system runs through the always-registered notifier. pi-subagents identifies a session by its **file path** (`getSessionFile() ?? getSessionId()`, shared/session-identity.js), so that set and Kady's Modal background-work provider use that identity; under the bare id the provider never matched and `bg_wait` could not see Modal jobs. `subagent-host.mjs` gates actual resolved model requests before calling the provider and sends idempotent usage receipts to `subagent-meter.ts` before releasing the terminal event. Detached runners use the authenticated loopback API and persist pending receipts under `.kady/subagent-usage-pending`; admission/completion drains receipts after outages. The legacy completion bridge prefers run-specific usage, never inherited fork totals, and skips already-metered sessions. Schedule completion adds origin metadata without a second charge. Model request costs are not reserved, so in-flight/concurrent requests can overshoot. External CLIs remain opt-in and unmetered.

- **Specialist fleet.** Automation contains `subagent-fleet-panel.tsx`: choose a chat, view models/tokens/activity, poll live transcripts, steer/stop/resume. `api/subagents.ts` invokes the plugin's versioned public RPC and verifies project/session/run/child membership before controls. Public snapshot rows receive canonical `{runId,index,childId}` through the pinned adapter; never derive control targets from display order or opaque `fleet-*` keys. Prompts and full skill trees from pi-subagents are seeded by `subagent-resources.ts`; its marker records the plugin version and each file's hash, so a plugin upgrade replaces copies still matching what Kady wrote (markers from before hashes use `LEGACY_SHIPPED_HASHES`, 0.73.1/0.74.0 — never extend it), adds entries the new version introduces once, upgrades disabled skills in `skills-disabled/`, and leaves edits and deletions alone. Agent frontmatter uses full YAML; unknown nested/typed fields round-trip via `extra`.

- **Workflow scripts are the delegation surface, and since pi-subagents 0.74 they live in the reply.** The model writes the script as one ```` ```js workflow ```` fenced block in its assistant message and calls `subagent({ workflow: true })` (since 0.76 a reply with no tagged block runs its only plain ```` ```js ```` block, and `"true"` is accepted for `true`); a `workflow` string containing `/` is a script file read from the request cwd, any other string a named workflow resource. The package's own named workflows take their children as data — `review` (one `reviewer`), `run-ci` (a host command, no model) and since 0.77 `parallel` (`args.tasks: [{ agent, task }]`, which the tool description now promotes for batches) — so `PACKAGE_WORKFLOWS` in `subagent-bridge.ts` reads their targets from `args`; a workflow another extension registered stays unreadable. Since 0.77 the model-facing schema keeps `agent`/`task`/`workflow`/`args`/`async`/`model`/`cwd`/`worktree`/`output`/`action`/`id`/`message` at the top level and moves every other field into an `options` object (top-level management fields still work); the guards walk the whole input, so both shapes are covered. `workflowScript`/`workflowScriptPath` were removed from the model-facing schema (model calls passing them are refused) and survive only as the plugin's internal carrier (schedules store `target.workflowScript`). Children are declared as `runs.run(key, { agent, task })`; a structured `{ agent, task }` call still launches one child, and top-level `model` is a per-run override forwarded to every child. Walking the tool input structurally sees nothing under that surface, so the guards in `subagent-bridge.ts` call `workflowCallTargets(input, { toolCallId, sessionManager, cwd })`, which reads the same script pi-subagents will run (`replyWorkflowScript` ports the plugin's non-exported `readReplyWorkflowScript`: Pi persists the assistant message before its tools run, so the block is on the branch when `tool_call` fires) and parses it with Acorn via `workflowScriptTargets()`, extracting literal agent/model properties without matching comments. A script it cannot read here (another extension's named workflow, missing file, zero or several blocks) and a computed name both report `dynamic`: gating then bills "unknown" (fail closed at the cap), and `pinWorkflowScriptModel` refuses to pin at all, because a per-run `model` outranks agent frontmatter, `agentOverrides.<name>.model`, and `subagents.defaultModel` (all checked first — see `settingsPinnedModels`). The chat renders the block collapsed as **Workflow script** (`web/src/lib/workflow-script.ts`, same fence rule). Launches default to **async**; the lead blocks on its children with **`bg_wait`**, which the lead's tool denylist (`LEAD_EXCLUDED_TOOLS`) must never name. Since 0.78 a session with `subagent` also declares `contact_supervisor` (so a fork inherits its parent's exact tool list and prompt cache; a lead call returns an error). pi-subagents also ships six **external-CLI builtins** (`claude-code`, `codex-exec`, `cursor-agent` and their `-writer` variants) that shell out to a locally installed and authenticated Claude Code / Codex / Cursor CLI, outside Kady's model runtime, ledger and spend cap; `subagent-runtime-settings.ts` seeds `agentOverrides.<name>.disabled: true` for them (write-if-missing, detected via `isExternalCliAgent`), so they show up off in Settings → Specialists and stay however the user toggles them. That tab's "Default model for specialists" writes project `subagents.defaultModel` in `sandbox/.pi/settings.json` (`GET/PUT /agents/defaults`, `setSubagentDefaultModel` in `agent-files.ts`; clearing deletes the key), so `defaults` is a reserved agent name (`RESERVED_AGENT_NAMES`) — the static route shadows `/agents/:name`. `pinInheritedChildModels` pins the parent model onto a structured (non-script) child only when neither `subagents.defaultModel` nor `agentOverrides.<name>.model` (nor frontmatter) names one, since the pin would outrank them.

- **Builtin tool overrides are reconciled, not just extended.** Builtin specialists pin a `tools:` allowlist that Pi also applies to package tools, so three bridges (notebook → modal → pdf-annotation, in that order) copy the declared list into `subagents.agentOverrides.<name>.tools` with their own group appended. That copy goes **stale** when an upstream release narrows a builtin (e.g. dropping `bash`/`edit`/`write` from `reviewer`): a settings file seeded earlier would hand the removed tools back. `server/src/agent/builtin-tool-overrides.ts` decides ownership by shape (drop tools the builtin no longer declares and that are not ours; does the remainder match something we generate?) and rewrites from the *current* frontmatter. A hand-written allowlist does not match and is left alone; a user addition to a Kady-shaped list is indistinguishable from an upstream removal and is dropped, which is the safe direction.

- **Verification gates, the verifier model and `/prove-verify`.** A brief that opens with "Verification gate:" switches any reviewer to an adversarial standard with an accept/repair/reject verdict; the definition lives in `CHILD_OPERATING_GUIDANCE` (so it reaches existing and custom personas) and the lead is told how to request it in `LEAD_DELEGATION_GUIDANCE`. `comparative-reviewer` (cross-attempt review) and `investigator` (one assigned direction → a checkable draft) joined the roster; `seedAgentFiles` offers roster additions once to existing projects, tracked in `.pi/agents/.seeded-names.json` (`LEGACY_SEEDED_ROSTER` stands in for older markers — never extend it). `SubagentType.verifier` plus `BUILTIN_VERIFIER_AGENTS` (`reviewer`, `evidence-auditor`) define the verifiers. Settings → Defaults → Verifier model (`defaults.verifierModel` in `kady-settings.json`) is projected by `agent/verifier-models.ts` into each project's `subagents.agentOverrides.<verifier>.model` — the only lever pi-subagents resolves per child for structured calls, workflow scripts (detached runner) and schedules alike. Kady owns only entries recorded in `.kady/verifier-models.json` (an edited value is released), skips verifiers with a frontmatter model (pi-subagents applies an override *over* frontmatter, so `requestedBillings` now checks `byAgent` first), and drops its entries while the model is unavailable (`modelRefAvailable` in session-registry). Reconciled at session build, in the ledger extension's `tool_call` hook before launches/schedule fires, and for every project on `PUT /settings/defaults`. `subagent-control.ts` appends `verifierModelGuidance` to the lead's delegation section while routing is active; `GET /agents` marks `verifier`/`verifierModel` rows. `/prove-verify` is prompt-only orchestration (no server loop): the lead keeps `derived/prove-verify/<run>/ledger.md`, runs one workflow per round, and checks a dollar limit with a `node -e` sum over `.kady/runs/*/costs.jsonl` since its start time. See `docs/sub-agents.md#verification`.

- **Specialist prompting.** `agent/subagent-prompts.ts` holds shared runtime guidance: `subagent-control.ts` adds the lead's task-brief/synthesis contract and the required `kady-child-runtime` extension adds child scope, clarification and handoff instructions. These are separate from editable personas in `subagents.ts`; use structured prompt sections and preserve Pi's forced prompt when its child context filter has already rewritten it. Role defaults remain seed-once (new projects or explicit Restore defaults); shared runtime guidance also reaches existing/custom personas. See `docs/sub-agents.md`.

- **Schedules + missions (server-owned).** pi-subagents arms schedule timers per live session and a fire produces no `tool_call`, so `server/src/agent/scheduler.ts` keeps one **resident session** per project with active schedules (id in `.kady/scheduler.json`, `markSystemSession` = pinned, excluded from `MAX_LIVE_PER_PROJECT`, hidden from `GET /sessions`), opened at boot and refreshed after successful schedule mutations via the `tool_result`-side `setScheduleActivityListener` (a hook, because bridge → scheduler → registry would cycle). The pinned adapter restricts project-wide timer arming, recovery and firing to the recorded resident session; a session-scoped `kady:schedules:refresh` event rereads the store after creation/resume so later schedules survive chat eviction without duplicate chat timers. Explicit `sessionOnly` schedules retain their original chat ownership. Panel actions and the budget hold call the `subagent` tool's `execute` directly on that session (`invokeSubagentAction`, no model), which skips the bridge's `tool_call` gate, so `api/automation.ts` re-applies the cap itself (402 for Run now and for resuming a `heldByBudget` schedule) and fires Run now with `quiet: true` (a noisy manual fire wakes the hidden resident session for a billed turn nobody sees); `mission.close` takes `missionStatus`, not `status` (an unknown key silently closes as `completed`). Fire results: pi-subagents drops success output, so the bridge's `subagent:async-complete` handler keeps a bounded copy in `.kady/schedule-outcomes.json` keyed by the async run id (`runId ?? id`, pi-subagents' own precedence), preferring each child's `artifactPaths.outputPath` inside the sandbox over the serialized workflow return; `listSchedules` attaches it as `runs[].summary`. `GET /subagents/sessions` lists the resident session once as "Scheduled runs" (filtered out of the chat rows first). The bridge gates `schedule.create` like a launch and refuses `schedule.run`/`run-due` over the cap; `reconcileBudgetHolds` (60s tick, `startSchedulerTick` in the `isMain` block only — never in `buildApp`) pauses active schedules while over the cap (`heldByBudget`) and resumes them after. `subagent:async-complete` carries `scheduleOrigin`, ledgered as `CostEntry.origin.schedule` (`scheduleSpend`). `api/automation.ts` reads pi-subagents' store (`sandbox/.pi/subagents/schedules/<id>/{schedule,history}.json`, owner paths stripped) and missions (`<agentDir>/missions/projects/<sha256(realpath(sandbox))>/*.json`, keyed by the real path since 0.77); UI is the project view's Automation tab (`automation-panel.tsx`). `AGENTS.md` v4 tells the lead to confirm interval/cost before scheduling.

- **Per-agent memory.** pi-subagents' `memory:` frontmatter is modelled in `agent-files.ts` as `AgentFile.memory` (`{scope: project|user, path}`), parsed and serialized as full YAML (both block and inline input forms work); `restoreDefaultAgents` carries an existing memory setting onto the rewritten roster file. `GET/PUT/DELETE /agents/:name/memory` read/edit/clear `<sandbox>/.pi/agent-memory/<path>/MEMORY.md` (or the user-scope file under `KADY_PI_AGENT_DIR`); the child creates it itself with `write`. Harvested child writes under dot-directories are already dropped by `resolveInSandbox` (`isUserVisible`), so memory writes never become provenance artifacts.

- **Supervisor channel + watchdog.** pi-subagents' `contact_supervisor` (child) / `subagent_supervisor` (parent, now in the lead allowlist and in both provenance read-only sets) delivers a child's question as a `subagent_supervisor_request` custom message with `triggerTurn: true`; the session observer adopts that turn as a system run, the SystemCard shows it, and the seeded `AGENTS.md` (v3) plus the `interview` tool's guidelines tell the lead to relay via `interview` and answer with `subagent_supervisor` reply (child timeout ≈10 min). The watchdog is configured in `sandbox/.pi/settings.json` → `subagents.watchdog` through `server/src/agent/watchdog-settings.ts` (`GET/PUT /watchdog`; strict upstream key set incl. `stalemateRepeats` 1–20, Kady always writes `lsp.enabled: false`, `WATCHDOG.md` seeded with scientific rules; only exact unchanged older shipped versions are upgraded; the card's number fields save on blur/Enter); findings arrive as `subagent_watchdog_warning` custom messages. Kady meters watchdog review and permission-review streams with the same admission and billing policy as children; default off. `GET /projects/:id/instructions` reports `agentsMdStatus` and `POST …/restore` rewrites the shipped text.
